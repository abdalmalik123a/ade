# D243 — نقل بيانات المكتب إلى جذر قرص (D:\DiwanData) بلا EPERM

> الوسم: ⚙️ (إصلاحٌ كشفته تجربة المالك لحزمة D242) · الحجم: ص · يعتمد على: D242 ✅ · بعده: إعادة بناء الحزمة وتجربتها ثانيةً

## الهدف
أوّل تشغيلٍ لـ2.0.0 على جهازٍ فيه بيانات سابقة يعرض «المقترح: D:\DiwanData» وينقلها إليه؛ وكان النقل يسقط بـ«EPERM: mkdir 'D:\'»
(سجلّ أخطاء جهاز المالك ٣٠ ت١)، فيبقى البرنامج على المكان القديم ويُسأل في كلّ تشغيل. بعد الأمر يُنقل إليه.

## اقرأ فقط
`src/main/services/dataLocation.ts` (`moveData`) · `tests/dataLocation.test.ts`.

## تحقّق قبل البدء
- `mkdirSync('D:\\', { recursive: true })` يرمي EPERM في Node وفي Electron نفسه خارج الحزمة (جُرّب) — فالخلل عامّ لا في MSIX وحده.
- والمقترح `suggestDataDir` في جذر قرصٍ دائمًا؛ وسيناريو dataLocation يجرّب مجلّدًا أعمق فلم يره.

## المسموح
`src/main/services/dataLocation.ts` و`tests/dataLocation.test.ts`، وPLAN والدفتر وهذا الأمر.

## الخطوات
1. اختبارٌ يسقط أوّلًا: هدفٌ في جذر قرص المؤقّت (`parse(tmp).root`) يُنقل إليه، ثم يُمحى.
2. `moveData`: لا يُنشأ أبٌ موجود (`existsSync(dirname(to))`) — والجذر موجودٌ دائمًا.

## الممنوع
لا تغيير للمقترح ولا للحوار ولا لطريقة النقل (نسخٌ ثم تحقّق، والقديم جانبًا).

## الفحص
`npx vitest run tests/dataLocation.test.ts`: الجديد ✗ قبل الإصلاح (EPERM على C:\) ثم ١٢ ✓ · `npm run typecheck`.

## الختام
✅ في PLAN، وقيدٌ، ونقلٌ إلى done، ثم إعادة بناء حزمة 2.0.0 وتسجيلها لتجربة المالك.
